# Аудит интерфейса, безопасности и быстродействия

Дата: 11 октября 2026. Объект: текущая рабочая копия Genshin-Impact-tg-bot, включая уже существовавшие незакоммиченные изменения.

Последующие исправления и повторная проверка: [отчёт об устранении находок](../audit-fixes-2026-10-11/REPORT.md). Ниже сохранён исходный результат аудита до исправлений.

Общий вывод: общая визуальная база есть, но экраны используют разные правила плотности, рамок и размеров управления. Самая серьёзная находка — воспроизведённое нарушение сохранения валюты при переводах из разных чатов. На слабых устройствах основные риски — загрузка всех механик при старте, постоянный WebGL и перекрывающиеся запросы обновления.

## Объём и достоверность

- Выполнен `node --test`: **926 тестов, 926 успешных**, 0 ошибок, 0 пропусков; около 134 секунд.
- Выполнен `npm audit --omit=dev --json`: **0 известных уязвимостей** в ответе реестра. Это проверка зависимостей, а не гарантия безопасности игровой логики.
- В Chromium проверены **11 реальных клиентских экранов × 2 ширины**: 320 и 390 px, высота 720 px, DPR 2. Персонаж, инвентарь, рыбалка, COL, аркада, сундуки, обменник, хранилище, магазин, обратная связь, справка.
- Использованы реальные JS/CSS и DTO из серверных модулей, API заменён локальными фикстурами. Проверка включает геометрию, вложенные рамки, размеры кнопок, ошибки JS и фокус. Это не проверка реальных Telegram-сессий или production MongoDB.
- В этих начальных состояниях нет горизонтального переполнения страницы/панели и ошибок JS. Намеренная горизонтальная прокрутка вкладок инвентаря остаётся.
- Экономический сценарий проверен на настоящих функциях перевода/синхронизации с моделью хранилища, повторяющей проверку ревизии MongoDB store. Некорректный Host проверен в изолированном HTTP callback с точной строкой парсинга из сервера.
- GPU probe доказывает продолжение отрисовки, но **не измеряет FPS/энергопотребление реального слабого телефона**. Не проверены все варианты всех игровых экранов, длинные списки клана, осады, реальные платежи и production proxy.

Приоритеты: P1 — исправить первым; P2 — следующая очередь; P3 — улучшение качества. «Воспроизведено» означает локальный сценарий; «по коду» — установленная причина без полного интеграционного воспроизведения.

## 1. P1 — валюта создаётся при переводах из разных чатов

**Воспроизведено на доменной логике.** Один персонаж имеет 100 золота. Две копии из разных чатов загружены одновременно. В первом чате он переводит 80 игроку B, во втором — 70 игроку C. Обе операции возвращают успех. После сохранения: отправитель 30, B 80, C 70, сумма **180 вместо 100**.

Причина: персонаж общий между чатами, а route lock привязан к `chatId`. В `persistChat` свежая устаревшая копия допускается к записи через `expectedRev=null`; реальный store при этом исключает `rev` из фильтра. В сценарии второе сохранение действительно использует `expectedRev:null`. Даже одинаковые суммы переводов не спасают: одинаковый hash может скрыть повторное списание.

Код: [characterSync.js:85](../../functions/general/characterSync.js#L85), [characterStore.js:20](../../functions/general/characterStore.js#L20), [server.js:911](../../miniapp/server.js#L911). Доказательство: [economy-probe.json](economy-probe.json).

Исправление: убрать обход CAS для финансовых изменений; сериализовать операции по общим персонажам в стабильном порядке, а не только по чату; сохранять списание и зачисление атомарно в MongoDB transaction. При конфликте повторять всю операцию после чтения актуального баланса. Одних process-local локов недостаточно для нескольких экземпляров сервера. Приёмочный сценарий: два параллельных перевода из разных чатов никогда не меняют суммарную валюту.

## 2. P1 — авторизация может сохранять Chat до route lock

**По коду; полный конфликт с MongoDB не воспроизводился.** `authorize()` вызывает `getSession()` до входа в лок маршрута. `getSession()` добавляет отсутствующего участника, нормализует поля/Telegram membership и вызывает `chat.save()` при изменениях. Bootstrap также сохраняет присутствие вне общего лока. Это оставляет путь записи в тот же документ в обход защиты игровых действий.

Код: [server.js:380](../../miniapp/server.js#L380), [getSession.js:45](../../functions/getters/getSession.js#L45), [server.js:468](../../miniapp/server.js#L468), [Chat.js:72](../../db/models/Chat.js#L72).

Последствия: конфликт версий, потеря обновления или непредсказуемый результат параллельных запросов; конкретный результат зависит от изменённых полей и hooks. Исправление: авторизация проверяет подпись/доступ без сохранения игровой модели; создание и нормализация выполняются под согласованными локами/транзакцией. Presence хранить отдельно или обновлять атомарно.

## 3. P2 — некорректный Host уходит в глобальный обработчик ошибок

**Воспроизведено в изолированном HTTP callback.** Запрос с `Host: [` вызывает `ERR_INVALID_URL` до любого `guarded()` и rate limit. За 300 мс ответ не отправлен. В основном приложении установлен global `unhandledRejection`, который синхронно пишет stack в `api.access.log`; поэтому утверждать, что production обязательно падает, нельзя. Возможны зависшие соединения и усиление нагрузки/роста лога. Доступность такого Host через production proxy не проверялась.

Код: [server.js:2160](../../miniapp/server.js#L2160), [errorHandler.js:9](../../errorHandler.js#L9). Доказательство: [url-probe.json](url-probe.json).

Исправление: внешний `try/catch` для всего HTTP callback, фиксированный base URL для разбора pathname, ответ 400 на неправильный URL; ошибки запросов не должны попадать в глобальный обработчик. Настроить ротацию лога.

## 4. P1 — все механики загружаются до первого экрана

**Измерен статический граф импортов.** `app.js` достигает **104 JS-модулей**, 1 200 897 байт исходников, около 345 288 байт при gzip каждого файла. Стартовая CSS-связка — **53 файла**, 492 086 байт исходников, около 98 274 байт gzip. Числа не включают картинки, Telegram SDK и динамические импорты.

CSS на сервере уже объединяется в один bundle, поэтому проблема не в 53 запросах CSS в production. JS остаётся раздельным графом статических модулей: браузер скачивает и разбирает клан, боссов, экипировку и другие механики ещё до их открытия. Крупнейший справочник иконок — около 160 КБ исходника.

Код: [app.js:2](../../webapp/app.js#L2), [server.js:240](../../miniapp/server.js#L240). Доказательство: [static-metrics.json](static-metrics.json).

Исправление: оставить в стартовом коде город/HUD/навигацию, открывать механики через динамические импорты; разделить большие справочники по назначению. CSS основных механик подгружать с сохранением порядка общих правил. Сравнить старт на ограниченной сети и CPU после изменений.

## 5. P2 — фон WebGL работает за окнами и при reduced motion

**Воспроизведено.** В режиме `prefers-reduced-motion: reduce`, с имитацией 4 CPU cores и открытым окном, probe за 1,2 секунды получил **16 вызовов drawArrays**. В других прогонах число отличалось, но отрисовка не прекращалась. Reduced motion учитывается для перехода, а не для основного frame loop. Есть ограничение DPR/FPS и пропуск draw при `document.hidden`, что уже полезно.

Код: [renderer.js:98](../../webapp/renderer.js#L98), [renderer.js:166](../../webapp/renderer.js#L166). Доказательство: [gpu-probe.json](gpu-probe.json).

Дополнительная цена: на всех проверенных экранах два слоя `backdrop-filter` — backdrop и panel; панель почти непрозрачна. Исправление: статический фон при reduced motion/режиме экономии, пауза WebGL за полностью перекрывающим окном; для слабых устройств отключать blur и использовать непрозрачную поверхность. Не привязывать качество только к deviceMemory: это значение доступно не во всех WebView.

## 6. P2 — polling допускает параллельные запросы и старые ответы

**По коду.** В боссе `pending` защищает пользовательские действия, но не устанавливается при polling. То же относится к охоте; в атласе `busy` также относится к действиям. Если ответ занимает больше интервала 2–2,5 с, новые запросы запускаются до завершения старого. Поздний старый ответ может заменить более новое состояние. В `app.api()` отсутствуют общий timeout и механизм отмены запроса. Poll босса не проверяет `document.hidden`.

Код: [boss.js:265](../../webapp/boss.js#L265), [hunt.js:435](../../webapp/hunt.js#L435), [world-map.js:67](../../webapp/world-map.js#L67), [app.js:101](../../webapp/app.js#L101).

Исправление: отдельный флаг запроса обновления, следующий `setTimeout` после завершения текущего, backoff на ошибках, pause при скрытии; версия/sequence ответа и отмена при закрытии. Timeout не означает, что сервер не выполнил POST: финансовые повторные операции требуют idempotency.

## 7. P2 — лишние рамки и padding сжимают рыбалку

**Измерено и просмотрено.** При viewport 320 px: внешняя панель 304 px, её контент 278 px, вложенный `.mmo-frame` имеет border + **16 px padding**, сцена внутри — **244 px**. До сцены теряется 76 px, почти 24% ширины экрана. При 390 px сцена 314 px. Рамка окна → декоративная рамка секции → рамка сцены дублируют оформление одной области.

Код: [fishing.js:139](../../webapp/fishing.js#L139), [boss.css:141](../../webapp/boss.css#L141), [design-system.css:464](../../webapp/design-system.css#L464). Иллюстрация: [fishing-320.png](fishing-320.png).

Исправление: одна внешняя поверхность; сцену и описание поместить непосредственно в content, сохранить разделение gap/заголовком. Снизить только декоративную вложенность, не уменьшать расстояния между зонами нажатия. Обычный 1px border сам по себе почти не съедает место; основная потеря — padding каждой вложенной коробки.

## 14. P3 — тяжёлая работа при первом запросе статики

**По коду.** Bundle собирается чтением всех CSS, холодное gzip-сжатие выполняется синхронно с level 9 в обработчике HTTP; для обычных файлов используются synchronous exists/stat. Кэш снижает повторную цену, но холодная работа блокирует общий Node event loop бота/API. В development bundle пересобирается на каждом вызове getPage(). Точная длительность на production CPU не измерялась.

Код: [server.js:230](../../miniapp/server.js#L230), [server.js:244](../../miniapp/server.js#L244).

Исправление: генерировать CSS/gzip на сборке или прогреть до приёма запросов; отдавать статику через proxy/CDN и при необходимости асинхронно сжимать. Сначала устранить стартовую загрузку и polling: они влияют на пользовательское устройство непосредственно.

## Очередь исправлений

1. Общая транзакционная экономика персонажа: межчатовые переводы, CAS, несколько получателей, конфликт сохранения.
2. Убрать записи из авторизации вне согласованного лока; обработать ошибки HTTP на внешней границе.
3. Ленивые импорты и последовательный polling с отменой/версиями ответа; статический режим GPU/blur.
4. Общие примитивы управления и модалок; исправить кошелёк, снять вложенные декоративные рамки рыбалки.
5. Явные темы персонажа/остальных окон, spacing scale, правка справки и компактность второстепенных текстов.

Приёмка: сохранение суммы валюты в конкурентных операциях; отсутствие overlap polling на задержке 5 с; отсутствие drawArrays в статическом режиме; целые числа баланса на 320 px; Tab не покидает верхнюю модалку; основные мобильные кнопки имеют согласованную hit area. Проверять реальные computed styles и сценарии, а не только наличие строк в исходниках.
